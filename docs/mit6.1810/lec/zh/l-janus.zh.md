6.1810 2025 第 7 讲：系统调用介入

不同风格的研究论文。
第一篇论文（"安全环境"）：研究人员阐述一个重要问题，提出解决方法。
第二篇论文（"陷阱与困境"）：反思为什么该方法被证明相当具有挑战性；学到的经验教训。
不是硬性能数字，而是意想不到的问题。
与我们上周阅读的 L4 论文有些不同。
L4 研究人员试图证明他们有好想法。
实证结果。

问题：应用程序代码不完全可信。
有错误的。
恶意的。
示例动机：网页浏览器（Netscape）运行 ghostscript 查看 ps 文件。
类似于运行 Acrobat 查看器查看 PDF 文件。
ghostscript 允许 ps 文件读取/写入其他文件，生成进程等。
PDF 文件存在类似问题，可以包含 Javascript 代码。
对手可能诱骗用户查看恶意构造的 ps 文件。

目标：最小化可能对抗过程造成的损害。
方法：限制可以发出的系统调用。
进程可以破坏它应该访问的文件，但不能破坏其他文件。
不应该能够杀死/破坏其他进程。

为什么是系统调用？
方便，现有的安全边界。
保护重要资源：其他进程，文件，网络。
不需要担心进程本身的状态。
不受信任的进程破坏自己的内存是可以的。
不需要修复应用程序。
很难重写每个应用程序使其安全。

我们能让内核直接支持沙箱吗？
内核通常提供一些安全检查（不是 xv6，而是 Unix 和其他）。
Unix 检查旨在隔离时间共享系统中的用户。
不受信任的进程不能破坏其他用户的数据，但可以破坏此用户。
设计选择如何影响应用程序可以/不能做什么的一个例子。

各种研究项目探索了灵活的 OS 安全机制。
将 Janus 放入内核对这些作者来说似乎不太好。
难以部署，需要管理员安装，可能有错误，..
回顾起来，许多操作系统现在在内核中支持沙箱机制。
Linux，Windows，MacOS，...
部分是为了避免论文讨论的陷阱/困境类型。
对内核支持它来说是足够重要的用例。

我们能在库级别进行沙箱吗--例如，调用 ulib？
例如，允许 printf，拒绝 write？
ulib/printf和应用程序其余部分之间没有隔离。
应用程序可能破坏栈，全局变量，malloc，...

系统调用接口已经为隔离而设计很重要。

你可能如何进行系统调用沙箱？
来自 syscall 实验的沙箱是一个很好的起点。
Unix 基线：ptrace。
存在许多限制，有更好的替代品。
Linux：Seccomp/BPF（更好的性能）。
Linux：AppArmor（与内核状态更紧密集成）。
Linux：Firejail（用户可配置的安全配置）。
MacOS：Seatbelt。
还有很多其他。

演示：Linux 上的 Firejail。
echo foo > ~/foo.txt
echo bar > ~/bar.txt
echo qux > ~/qux.txt
cat example.profile
firejail --profile=example.profile sh
ls
cat foo.txt
cat bar.txt
echo hello > foo.txt
echo hello > bar.txt

Janus 设计：内核模块 + 用户空间策略。
拦截系统调用，一些标记为敏感（可能不是 read/write）。
对性能关键的非敏感系统调用的性能优化。
将敏感系统调用发送到特殊 Janus 进程：策略引擎。
决定是否允许/拒绝。
常见设计模式：内核存根与用户空间辅助进程。
用户空间进程：更容易开发，减轻错误，用户可配置。
内核部分：直接访问否则不可能的内核状态。
需要在这两部分之间设计特殊的系统调用接口。

为什么在系统调用级别进行沙箱很困难？
主要挑战：系统调用没有所有决策所需的信息。
指针 0x1234 是好是坏？
取决于调用者地址空间中的内容。
文件"x"是好是坏？
取决于当前工作目录。
路径"a/b/c"是好是坏？
取决于"a"和"a/b"和"a/b/c"是什么。
文件描述符 5 是好是坏？
取决于 FD 表条目中的内容。

Unix 系统调用有一些好的方面。
比方说，比 L4 系统调用（主要是发送/接收）有更多信息。
路径名操作与访问打开的文件描述符分开。
在文件打开时介入，然后允许任何打开的 FD 读/写。
阻止创建网络套接字的调用，但仍允许 FD 读/写。

挑战：复制内核代码/状态。
可以尝试维护内核状态的副本来做决策。
例如，跟踪文件描述符。
例如，跟踪当前工作目录。
例如，实现路径遍历逻辑。
但细微的角落情况可能导致状态分歧。

挑战：宽接口，意外交互。
崩溃导致内核将核心转储写入"core"文件。
没有打开系统调用。
文件描述符传递。
绕过打开系统调用的检查。
可能绕过策略的辅助进程（不仅限于内核）。

挑战：TOCTTOU。
在做决策时状态发生变化。
符号链接。
在目录重命名发生时的目录遍历。
当前工作目录。
内存参数。
文件描述符。

挑战：强制执行系统调用 API 的子集。
拒绝创建符号链接。
拒绝重命名符号链接。
拒绝通过符号链接访问（O_NOFOLLOW）。
问题：在最终组件之前路径遍历期间的符号链接。
最近的 API：openat2 RESOLVE_NO_SYMLINKS。

挑战：阻止重要的系统调用。
阻止系统调用可以改变程序行为。
可以使行为良好的程序做错事。
例如，可能阻止它放弃自己的特权，关闭 fd 等。

这些中哪些可能是 xv6 中的问题？

系统调用介入在实践中经常使用。
大胜利：不需要修改应用程序。
大胜利：即使应用程序是恶意的也能监控/执行。
隔离，审计，入侵检测，...

如何避免这些陷阱？
内核介入而不是用户空间 ptrace。
在使用用户内存作为系统调用参数之前复制它。
与内核代码路径集成而不是在操作前检查。
通过修改沙箱应用程序来强制"良好行为"。
将路径遍历展开为易于检查/沙箱的步骤。
不适用于每个系统调用，但对于某些应用程序可以工作。
