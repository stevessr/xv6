Mogul 和 Ramakrishnan 的"在中断驱动内核中消除接收活锁"的常见问题，1996 年。

Q: 论文关注的活锁问题是什么？
A: 当数据包到达速度如此之快，以致 CPU 花费大部分或全部时间在网卡中断处理程序中，将数据包从网卡的接收 DMA 环移动到软件 IP 输入队列时，就会出现活锁。这使得很少或没有 CPU 时间来执行执行 IP 处理的线程，因此数据包没有从 IP 输入队列移动到输出网卡。结果是 IP 输入队列增长到最大允许长度，从那时起，网卡中断处理程序丢弃大部分或全部到达的数据包。论文建议的解决方案是在高负载下禁用中断，并有一个轮询线程直接从网卡读取数据包（没有 IP 输入队列），执行所有 IP 处理，并将数据包交给输出网卡。这解决了活锁问题，因为在负载高时没有中断，因此没有在网卡中断处理程序中花费过多时间的危险。网卡的第一个中断唤醒轮询线程，之后中断被禁用。轮询线程从输入设备移动一批数据包，通过 IP 处理，然后到输出设备，包括所有输出设备处理。在完全处理网卡 RX DMA 环中的所有数据包后，轮询线程重新启用中断并回到睡眠状态。

Q: 什么是链路层处理？
A: 发送和接收数据包所需的低级机制。这通常包括将位编码为电信号和标记数据包之间的边界。https://en.wikipedia.org/wiki/Data_link_layer

Q: 第 6.4 节指出不能使用内核的线程调度程序来模拟处理数据包的循环调度。为什么？
A: 一个可能效果不佳的方法是每个网络接口有一个轮询线程，或一个发送线程和一个接收线程，并依赖普通线程调度程序来决定何时运行每个线程。在高负载下，调度程序只会由于时钟中断而切换线程。但这可能不够频繁——数据包到达如此之快，以至于在时钟中断间隔内输入队列可能会溢出。

Q: 轮询是否会导致数据包处理的低延迟？
A: 答案取决于你愿意投入多少 CPU 时间进行轮询。如果计算机没有其他事情要做，因此可以几乎将其所有时间用于轮询循环检查最近到达的数据包，那么轮询可以提供非常低的延迟，比中断更低。但如果计算机需要花费时间做轮询循环以外的事情，因此不能经常检查新到达的数据包，中断可以提供更低的延迟。

Q: 当网络轮询线程活跃时，内核调度程序会在它和用户进程（如 screend）之间进行上下文切换吗？
A: 我怀疑作者的操作系统会在想要运行的内核线程之间进行调度，但内核线程具有相对于用户级执行的绝对优先级。而且作者使用的是单处理器（只有一个核心）。所以在轮询线程想要运行的时间内，没有用户级代码会运行。这是第 6.6.1 节/图 6-4 结果的一个要素："反馈"机制导致轮询线程睡眠，允许用户级 screend 程序运行。

Q: 如果输入数据包率很高，论文的轮询方案会导致丢弃数据包吗？
A: 是的。使用论文的轮询方案，如果数据包到达速度超过计算机处理速度，那么首先网卡硬件将在内部队列中缓冲多余的数据包，当网卡用完缓冲空间时，它将开始丢弃传入的数据包。任何无法跟上最大可能输入率的设计都必须在高负载下丢弃数据包。论文的关键见解是最好在最早的可能时刻丢弃多余的数据包，以避免浪费 CPU 时间来部分处理稍后将被丢弃的数据包。

Q: 什么是 screend？
A: screend 在路由器上实现网络防火墙，以防御来自较大互联网的不需要的流量。内核网络代码向 screend 显示每个数据包，screend 查看数据包并告诉内核是否可以转发该数据包。screend 是一个用户级程序（不是内核的一部分），内核维护一个等待 screend 查看的数据包队列。您可以在这里了解更多：https://citeseerx.ist.psu.edu/document?repid=rep1&type=pdf&doi=a822dc4058040a5a3866af897d9af9f618ba83ed http://bitsavers.informatik.uni-stuttgart.de/pdf/dec/tech_reports/NSL-TN-2.pdf

Q: 现在的计算机比 1996 年快得多。这是否使活锁问题消失了？
A: 更快的 CPU 只有在 CPU 如此之快以至于可以处理网络可能提供的峰值负载时才有帮助。但是网络变得和 CPU 变得一样快，所以我们仍然处于网络流量很容易压倒计算机的情况。另一方面，这篇论文促使 O/S 设计者采取措施避免活锁。例如，Linux 的 NAPI 是一个受活锁论文启发的自适应轮询方案：https://www.usenix.org/legacy/publications/library/proceedings/als01/full_papers/jamal/jamal.pdf https://lwn.net/Articles/833840/ 一些硬件改进也有所帮助。现代网卡实现"中断调节"，可以限制它们生成中断的速率（无论数据包到达速率如何）。现代 CPU 有多核，这使得轮询更容易（一个核心可以轮询而其他核心做其他工作）。

Q: 什么是流量控制和非流量控制协议？
A: 流量控制协议，如 TCP，仅当接收方表示准备就绪时才允许发送方发送新数据。流量控制协议不太可能出现活锁：如果接收方由于高数据包到达率而跟不上，它将自动停止要求发送方发送新数据，发送方将停止发送。非流量控制协议没有这种从接收方向发送方的反馈：发送方会继续以它选择的任何速率发送，而不考虑接收方发生的情况。一些实时音频和视频流协议就是这样工作的。所以即使接收方正在经历过载和活锁，发送方也不会减速。

Q: 作者提出的设似乎在输入速率太高时会丢弃数据包。这对于发送网络数据的应用程序来说不好吗？
A: 是的，如果路由器丢弃的数据包超过一小部分，高级协议和应用程序可能会表现得很差。可靠协议如 TCP 将在超时后检测到丢失的数据包并重新发送；接收方将体验这些超时延迟；重新发送进一步增加了路由器的负载。不重新传输的协议在有大量数据包丢失时会遇到其他问题（例如音频中断）。网络运营商试图确保网络组件（路由器、链路等）足够快，以处理普通高负载，以避免需要丢弃数据包。然而，总有意外：例如，某些新应用程序可能突然变得流行（很久以前的 Web；流式音频；流式视频），给网络带来意外的高负载。从长远来看，网络运营商可能必须购买更高性能的设备。在短期内，网络如何处理突然过载很重要。过载不可避免地导致丢弃数据包，即使在没有活锁或其他类似问题的系统中。但最好只丢弃减少数据包率到网络和路由器能处理的程度所需的数量。论文解决的活锁问题是丢弃了比必要更多的数据包。

Q: 论文的测量使用了什么样的网卡？
A: 网卡是"AMD LANCE"。LANCE 类似于 net lab 的 e1000，具有 RX 和 TX DMA 描述符环。默认情况下，像 e1000 一样，它在数据包到达时以及网卡完成发送传出数据包时中断。

Q: 论文说最好尽可能早地丢弃数据包。论文的设计如何决定丢弃哪些数据包？
A: 论文的设计，在第 6.4 节中，没有明确决定何时丢弃数据包。相反，第 6.4 节的设计尽可能快地处理数据包。如果数据包到达速率高于软件可以处理的速率，软件无法足够快地清空网卡的接收 DMA 环。所以在这种情况下，DMA 环经常是满的。在这种情况下，网卡丢弃传入的数据包，软件永远不会看到它们。网卡丢弃多余数据包的好处是这些数据包不会消耗 CPU 时间，因此不会导致活锁。理想情况下，路由器会做出明确的丢弃决策，例如优先丢弃最低优先级或最不重要的数据包。当导致丢弃的瓶颈是慢输出链路，并且有足够 CPU 时间查看所有传入数据包时，这是可能的。但论文探讨的是负载如此之高，以至于路由器没有足够 CPU 时间查看所有数据包，因此无法做出巧妙丢弃决策的情况。现代网卡是相当可编程的，支持多个 DMA 环，可以告诉它将不同类型接收到的数据包放在不同 DMA 环上。聪明的路由器可以使用此功能在过载下优先处理流量。
