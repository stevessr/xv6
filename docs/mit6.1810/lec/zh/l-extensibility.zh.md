标题：内核可扩展性
作者：Sanjit Bhat (sanjit.bhat@gmail.com)

广泛来说：能够动态更新内核。
图：[用户] \--- [内核] [[而不是严格分离]] [用户 + 模块] \--- [发送模块] [内核 + 模块]

为什么这有用：
1. 可观察性：看到内核中发生的事情。
2. 性能：让内核为我们做更多/更好的事情。
3. 安全性：为事物指定更复杂的允许/拒绝过滤器。

演示示例（来自 https://github.com/iovisor/bcc）：
1. 在进程启动时打印'hello world'。
- 钩接到进程克隆。
```
$ sudo python3 ~/bcc/examples/hello_word.py
```
2. 磁盘操作的延迟分布。
- 测量 I/O 请求和设备完成之间的延迟。
- 定期计算百分位数。
```
$ sudo python3 ~/bcc/examples/tracing/biolatpcts.py
$ python3 file-gen.py
```
3. DDOS 攻击检测。
- 早期拦截数据包，这样它们就不会压倒我们的系统。
- 配置内核测量数据包之间的时间差异。
- 当差异足够大时发出警报。
```
$ sudo python3 ~/bcc/examples/tracing/dddos.py
$ sudo hping3 localhost -S -A -V -p 443 -i u100
```

这如何可能工作？
1. 在内核中运行任意二进制文件？
2. 只运行来自"受信任"方的二进制文件？
3. 以某种方式约束二进制文件？
4. 完全跳过内核？

这些都有权衡，我们稍后会重新讨论替代方法。
eBPF 使用二进制约束方法。
让我们用规范的 cBPF（eBPF 前身）示例深入探讨。

tcpdump - 执行网络监控的实用程序。
让我们要求它获取所有 TCP 连接，包括我的 SSH 连接。
```
$ sudo tcpdump -p -ni enp0s1 -d "ip and tcp"
(000) ldh [12]
(001) jeq #0x800 jt 2 jf 5
(002) ldb [23]
(003) jeq #0x6 jt 4 jf 5
(004) ret #262144
(005) ret #0
```

观察：哇，这里有汇编型指令！
它是如何工作的？
图：[用户：tcpdump -> bpf 程序] \--- [发送程序] [内核 + bpf 程序]

但等等，这些真的是本机 OS 架构中的指令吗？
cBPF 抽象机器：
寄存器：acc，idx。
内存：数据包，临时。
操作：ld，st，jmp，（算术），ret，tax。

以太网帧：[目标 MAC | 源 MAC | 以太类型 | 数据]
      6B    6B    2B
IP 帧：[头 1 | 长度 | 头 2 | 协议 | 校验和 | 源 | 目标 | 数据]
     2B  2B   5B  1B   2B    4B  4B

cBPF 代码注释：
0: acc <- P[12] (以太类型)
1: j (acc == IP)
2: acc <- P[23] (IP 协议)
3: j (acc == TCP)
4: ret 数据包长度
5: ret false

这种不同的架构如何执行？
解释器：
- 读取 cBPF 程序的 C 程序。
- "仿真"语言。
- 为了效率，在与内核相同的地址空间中运行。

精炼图：[用户：tcpdump -> bpf 程序] \--- [发送程序] [内核 + 解释器 (bpf 程序)] <-- 两者都在相同地址空间

房间里的大象：
问：由于这是一种读取/写入数据包数据的类似汇编的语言，这是否破坏了隔离？
答：记住，eBPF 的计划约束二进制文件，但如何约束？
数据包过滤的安全威胁模型：
- 允许非 root（恶意）进程运行程序。
- 允许读取寄存器、数据包内存、临时内存。
- 允许写入寄存器和临时内存。
- 禁止读取/写入之外的内容。

恶意程序的例子是什么？
```
(000) ldh [大数]
```
- 读取超过数据包内存末尾到其他内核内存。

问：如何禁止？
答：预先查看程序并禁止大偏移。
对于非恒定偏移，我们怎么做？
```
(000) ldx 4*([14]&0xf) // 根据IP长度将TCP偏移加载到idx寄存器。
(001) ldh [x+16] // 加载TCP目标端口。
```
- 总偏移包括 TCP 长度。
- 我们可以对其设置最大边界，但那样会过度近似偏移。
- 相反，必须在解释器运行时检查实际偏移。

到目前为止，我们一直在描述 cBPF（v2.5，2001）。
只在 net 钩子上进行数据包过滤。
随着时间推移，人们想要更多速度和通用性（即，在不仅仅是网络的更多子系统中使用 eBPF）。

速度：解释器慢（为什么人们总是抱怨 Python 速度慢？）。
仿真程序 vs.直接运行它。
BPF 看起来与实际架构如此相似，所以让我们直接编译到一个。
JIT 编译器（v3.0，2011）。

通用性：钩入系统调用、函数入口/出口、存储堆栈等。
新 eBPF 语言（v3.18，2014）看起来更像本机架构。
寄存器：11（R0 - R10）。
宽度 32 -> 64 位。
内存：栈（cBPF 临时），上下文（cBPF 数据包），映射（允许用户空间通信和持久）。
函数：调用 bpf 助手。

隔离：
- 取决于用例。
- 仍然相当受限，除了 bpf 调用。
- 即，不能原生获取任意内核指针并解引用。
- 需要使用 bpf 调用来做到这一点。

让我们回到隔离。
问：我们如何处理 JIT 代码的非常数偏移？
答：我们之前做的运行时指针值检查不可行。
那么我们如何做到呢？
目标：跟踪指针值，但不能在运行时做到。
解决方案：完整的符号执行。
- 模拟所有可能的程序路径。
- 跟踪指针值。
- 确保它们在边界内。

验证器介绍：
1. 将值拆分为 PTR 和 SCALAR。
SCALAR 永远不能用作内存地址。
2. 跟踪值的传递。
示例值跟踪：
```
R1 开始PTR，按定义它是指向ctx的指针
R1=R2? 错，因为R2未初始化。
R2=R1+R1。R2类型应该是什么？SCALAR。
ret R1? 取决于排序和程序。
在某些程序中返回PTR是不允许的。
KASLR。
R3 = R10-8
R4 = *R3? 不，因为未初始化。
*R3 = R1
R4 = *R3? R3类型？PTR。
*(R3 + 10) = 5? 不，因为OOB。
R5 = map[0]
if R5 < 8:
R4 = *(R3 + R5)? 好，因为if分支。
R4 = *(R3 + R5)? 不好，因为其他if分支。
```

这些指针似乎真的很麻烦。
如何跟踪它们？
1. 固定（完全已知）偏移和可变偏移。
对于可变偏移：
1. 最小/最大有符号/无符号，32/64 位。
2. Tnum：单个位的知识。
- mask = 1，未知。= 0，已知。
- 如果已知，值是实际位。

示例：
```
R2 (mask=0b0011, val=0b1000)
R3 |= 0b1 (mask=0b0010, val=0b1001)
R3 &= 0b00 (mask=0b0000, val=0b1001) (mask=0b1, val=0b1)? 不，那会违反tnum的一些不变量。
```
```
R5 = map[0] (min=0, max=MAXVAL)
R6 = R5 + 5 (min=5, max=MAXVAL) // 这里tnum？难。
if R5 < 8:
R5 (min=0, max=8)
这里tnum？难。
R5 (min=0, max=MAXVAL)
R6 = R5 | 0b1 (mask=0b1..0, val=0b0..1) // 这里寄存器边界？难。
```

eBPF 验证器做一些相当复杂的数学。
让我们形式化验证 eBPF 验证器。
参考：https://sanjit-bhat.github.io/assets/pdf/ebpf-verifier-range-analysis22.pdf。
跟踪添加两个数字的范围函数的规范：
```
{{{ ∀ x y, oldRng1.contains(x) ∧ oldRng1.wf() ∧ oldRng2.contains(y) ∧ oldRng2.wf() }}}
addRanges(oldRng1, oldRng2)
{{{ RET (newRng1); ∀ z, z = x + y → newRng1.contains(z) ∧ newRng1.wf() }}}
```
- 包含是直观的。例如，min <= x <= max。
- Wf（良好形式）编码范围的不变量。例如，min <= max。

其他验证器事项：
1. 修剪。当 CFG 子图的验证器路径被另一条路径包含时的概念。
如果你已经检查了另一条路径，无需检查这条路径。
2. 活跃度跟踪。帮助修剪。
3. 修剪需要：
- 积极，跟踪精确状态以减少符号执行路径。
- 不太积极以至于不安全。

但...
它真的有多通用？
是否应该只在所有地方添加钩子？
让我们通过一些扩展 eBPF 需要小心的示例。

eBPF 直接调用内核函数。
- 编译为调用指令。
- 现在跨越"架构"调用。
- 不同调用约定。
- R6-R9 被调用者保存。所以得到它们回来。
- R1-R5 调用者保存。被破坏。调用后无法使用。
需要在验证器中跟踪。
- 另外，内核函数并非设计为从"敌对调用者"调用。
- eBPF 验证器做最小检查以查看调用是否"安全"。
- 参见 https://lwn.net/Articles/856005/。
- 参见 https://sigops.org/s/conferences/hotos/2023/papers/jia.pdf。

非特权 eBPF：
- 之前，允许某些低能力程序如套接字过滤器。
- 现在，有很多验证器错误。
- 所以我们在一些中间状态。
+ 只有 root 可以调用 eBPF 程序。
+ 它们不能是恶意的。
+ 但我们也不希望它们搞乱内核？所以需要一些验证器检查。
- 威胁模型更复杂。
- 参见 https://lwn.net/Articles/796328/。

调度器中的 eBPF：
- 似乎有用。允许用户为他们的特定应用程序定制调度。
- 例如，在虚拟化 Linux 中，最小化主机调度程序与客户调度程序的干扰。
- 然而，调度器是内核如此重要的部分，我们真的想要用户有自己的吗？
- 这可能会阻止全局修补调度程序错误和碎片化调度程序生态系统。
- 参见 https://lwn.net/Articles/873244/。

可睡眠 eBPF 程序：
- 如果你想要一个接受用户空间指针的 eBPF 程序（例如，一些安全程序）如何？
- 指针并不总是映射，所以访问它可能会导致页面错误...在程序期间。
- 但 eBPF 程序不是为了被阻塞的。
- 阻塞实际上会导致很多问题，例如，与映射 RCU 或关键路径网络钩子。
- 所以要非常小心你允许哪些程序成为可睡眠，甚至更多地约束它们。
- 参见 https://lwn.net/Articles/825415/。

大担忧：eBPF 真的是可扩展性的正确方法吗？
- eBPF：允许更容易的内核修改。
- 另一个选项：绕过内核并直接将数据发送到用户空间。
- 优点：无需设计特殊钩子或验证器。
- 缺点：可能需要特殊硬件。
- 参见 https://irenezhang.net/papers/demikernel-sosp21.pdf。

结论：
- eBPF 启用了很多很酷的东西。
- 它的隔离由复杂的验证器提供支持。
- 但不是可扩展性的灵丹妙药。
- 需要仔细考虑不要破坏隔离。
