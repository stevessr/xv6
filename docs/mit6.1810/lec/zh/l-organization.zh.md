6.1810 2025 L4：操作系统组织，微内核

主题：内核应该做什么？
它的抽象/系统调用应该是什么样的？
可能有不止一种方法吗？

这个主题更多关于想法，而不是具体的机制

"传统方法" -- UNIX, Linux, xv6
1) 大抽象，和
2) "单体内核"实现

大抽象示例：具有名称、目录、权限等的文件系统；对于程序员：便利性、可移植性
例如 vs 原始磁盘
对于内核：帮助共享和管理资源
例如 内核负责为不同程序分配磁盘空间
对于内核：帮助安全
例如 文件权限

大抽象导致大"单体内核"
内核是一个大程序，像 xv6
内核子系统易于合作 -- 没有烦人的边界
exec() 与内核的进程、内存和文件代码集成
所有内核代码以高权限运行 -- 没有内部安全限制

单体内核/大抽象有什么问题？
大 => 复杂 => 可能有错误/不安全
过度通用 => 可能慢
通过 UNIX 管道发送一个字节需要执行多少代码？
缓冲、锁、睡眠/唤醒、调度器
大抽象隐藏/强制执行许多设计决策，可能很尴尬
也许我想等待一个不是我孩子的孩子进程
也许我想改变另一个进程的地址空间
也许数据库比内核文件系统更好地在磁盘上布局 B-Tree 文件

微内核 -- 一种不同的方法 -- 例如 L4, Mach
主要目标：尽可能简单的内核
主要技术：将大多数 O/S 功能移到用户空间服务进程
[图：硬件，内核，应用程序，服务（文件系统 磁盘 虚拟内存 TCP 网卡 显示器）]

内核提供什么？
地址空间、内存管理、线程、IPC
IPC = 进程间通信
1980 年代见证了微内核设计研究的大爆发
CMU 的 Mach 可能是最有影响力的

人们对微内核希望获得什么？
白纸 -> 更优雅
小 -> 错误更少 -> 更安全
小 -> 可验证（参见 seL4）
小 -> 更容易优化
小 -> 对应用程序强制执行更少的设计决策
用户级 -> 强制更模块化的 O/S 服务
用户级 -> 更容易扩展/定制/替换用户级服务
用户级 -> 更健壮 -- 重启单个用户级服务
大多数错误在驱动程序中，把它们从内核中拿出来！

与例如 Linux 相比，L4 内核中没有什么？
几乎所有！
文件系统、fork()、exec()、管道、设备驱动、网络堆栈等；

如果你想要这些，它们必须是用户级代码
库或服务器进程
并建立在 L4 确实提供的少量功能之上

L4 系统调用：
创建任务/地址空间
创建/销毁线程
通过 IPC 发送/接收消息（地址是线程 ID）
拦截另一个地址空间的页面错误 -- "分页器"
并更改目标的映射
访问设备硬件
通过 IPC 接收设备中断

示例：L4 上的 exec()
现有任务 T1 想要创建新任务并让它执行文件中的指令
假设有一个文件系统用户级服务
1. T1 创建新任务 T2 -- 它将没有内存！
2. T1 告诉 L4 启动 T2 在 PC=0 执行
3. T2 将立即访问无效内存并发生页面错误
4. L4 内核通过 IPC 将页面错误信息发送给 T1
5. T1 通过 IPC 请求文件系统服务器读取文件块
6. T1 现在在其内存中有文件块
7. T1 告诉 L4 将文件块映射到 T2 的内存中，并恢复 T2
（页面错误驱动的文件访问通常称为"按需分页"）

问题：IPC 性能
微内核程序做大量 IPC！
在早期系统中很昂贵
多次内核交叉、缓存未命中、上下文切换等；
IPC 成本导致许多人否定微内核
L4 设计师在 IPC 性能上投入巨大努力

这里是一个缓慢的 IPC 设计，模仿 UNIX 管道
[图，内核中的消息队列]
send(id, msg) 将 msg 复制到内核中的队列，返回
recv(&id;, &data;) 如果队列中有 msg，复制到用户空间，返回
否则等待调用 send() 称为"异步"和"缓冲"
通常的请求 - 响应模式（RPC）将是：
[图：回复的第二个消息队列]
4 个系统调用（用户->内核->用户）
send() recv() recv() send()（recv() 返回）
或者八次用户/内核或内核/用户交叉
每次都很慢！
四次消息复制（请求两次，回复两次）

L4 的快速 IPC
"通过内核设计改进 IPC，" Jochen Liedtke, 1993
* 组合 call() 和 sendrecv() 系统调用
IPC 几乎总是用作请求 - 响应 RPC
因此使用单独的 send() 和 recv() 系统调用是浪费的
[图]
客户端：call()：发送消息，获得响应
服务器：sendrecv()：回复一个请求，等待下一个
用户/内核交叉减少 2 倍

* 同步
[图]
call() 等待目标线程的 sendrecv()
常见情况：目标已经在 sendrecv() 中等待
call() 返回到目标，就像从 sendrecv() 返回一样

* 无缓冲同步 => 源和目标用户缓冲区地址都知道 => 直接复制
无需复制到/从内核缓冲区

* 小消息在寄存器中，不在内存中
* 大消息作为页映射
send() 将发送者的页映射到目标的地址空间
recv() 指定目标中的地址
再次，无需复制

* 小心布局内核代码以最小化缓存足迹
结果：IPC 成本减少 20 倍
在这种情况下，简单性确实实现了优化 -- 很好。

如何在微内核上构建完整的操作系统？
需要一组用户级服务器。
文件系统、设备驱动、网络堆栈等；
对于嵌入式系统，这可以相当简单。
对于通用用途的服务，例如工作站、Web 服务器呢？
真的需要与现有应用程序的兼容性。
例如 系统需要模仿类似 UNIX 的东西。
重新实现 UNIX 内核服务作为许多用户级服务任务？
想法：在微内核上运行现有 Linux 内核作为进程。
一个"O/S 服务器"。
也许不优雅，但实用。
采用之路的一部分：用户可能开始只是运行 Linux 应用程序。
然后逐渐利用底层微内核的可能性。

运行用户级 Linux 内核意味着什么？
Linux 内核只是一个程序！
作者以小方式修改了 Linux
用 L4 系统调用或 IPC 替换硬件访问。
进程创建、配置用户页表、用户内存分配、系统调用处理、中断处理。
对 Linux 文件系统、网络协议、设备驱动等没有改变；

L4/Linux系统调用通过IPC
每个 Linux 进程是一个 L4 任务
Linux 服务器主要是单个 L4 线程，等待 IPC
系统调用：IPC 到 Linux 服务器（进程阻塞，等待 IPC 回复）
Linux 服务器执行系统调用实现
发送 IPC 回复（L4 交付，进程可以恢复）
Linux 服务器等待下一个系统调用 IPC
L4/Linux服务器分配所有内存，分发给进程
所以所有用户内存也映射到 Linux 服务器的地址空间
使用它进行 copyin()/copyout()，从系统调用中解引用用户指针
这让系统调用 IPC 变小 -- 数据地址，而不是数据本身
Linux 服务器还使用其内存访问进行 fork() 和 exec()

示例：L4/Linux 的 fork() 如何工作？
进程 P1 调用 fork()(P1 实际上是一个 L4 任务)
P1 的 libc 库将 fork() 转换为到 L4/Linux 服务器的 IPC
L4/Linux为P2分配一些页面，复制P1的内存。
L4/Linux要求L4创建新任务 -- P2
L4/Linux向P2发送特殊IPC，包含SP和PC以使其运行
L4/Linux从P2获得外部分页器错误，逐个映射页面

Linux：1.68 微秒
L4/Linux：3.95微秒

整体系统基准测试：AIM 图 8
AIM 分叉一堆进程
每个随机使用磁盘，分配内存，使用管道，计算等；
做固定总量的工作
x 轴显示[一些函数]并发 AIM 进程的数量
因此总工作量
y 轴显示完成所有工作的时间
只有斜率真的重要
斜率是每单位工作的时间，所以越低越好
本地 Linux 是最好的，但 L4Linux 只慢一点点
Mach+Linux 明显效率较低

结论：
2 倍 IPC 时间似乎对整体没有太大差异
L4+Linux 只比 Linux 慢一点点
L4+Linux 比 Mach+Linux 明显更快
这些结果本身并不是使用 L4 的论据
但它们是反对因性能担忧而拒绝 L4 的论据
