*** 虚拟机

什么是虚拟机？
计算机的模拟，准确到足以运行操作系统
图：硬件，宿主/VMM，客户 linux 和应用程序，客户 Windows 和应用程序
VMM 可能是独立的，或者 VMM 可能在宿主操作系统中运行，例如 Linux

为什么使用虚拟机？
云：每台物理机器上运行许多客户机实例
每个客户可以运行他们想要的任何操作系统等在他们的虚拟机中
云可以在许多客户之间共享每台机器
隔离，比例如进程迁移、复制更严重
软件开发人员：用于测试的虚拟"崩溃"盒子（听起来熟悉吗？）
虚拟机有悠久历史
1960 年代：IBM 使用虚拟机来共享大型昂贵的机器
1980 年代：（计算机变得小型且便宜）
（然后机房满了）
1990 年代：VMWare 重新普及了虚拟机，用于 x86 硬件
2000 年代：在云、企业中广泛使用

为什么在 6.1810 中看虚拟机？
VMM 与操作系统内核有很多共同点
操作系统设计中一些最有趣的动作已经转移到了虚拟机
虚拟机既影响了操作系统（上面）也影响了硬件（下面）

虚拟机必须有多准确？
通常目标是 100% 准确性
无需修改即可启动任何客户操作系统
防止恶意客户突破
客户甚至无法检测是否在虚拟机中！
实际上，VMM 和操作系统经常合作以提高效率
例如，VMM 提供客户知道的特殊磁盘/网络"设备"

我们可以通过编写软件来模拟机器指令来构建虚拟机
VMM 解释每个客户指令
为客户维护虚拟机状态
32 个寄存器，satp，模式，RAM，磁盘，网络等
优点：这有效，例如 qemu
缺点：慢
想法：直接在 CPU 上执行客户指令--快！

如果客户内核执行特权指令会怎样？
例如，客户将新页表加载到 satp 中
想法：在用户模式下运行客户内核
类似于将客户内核作为 xv6 进程运行
当然，客户内核假设它在管理模式下
普通指令工作正常
添加两个寄存器，函数调用等
特权 RISC-V 指令在用户模式下是非法的
会导致陷阱，到 VMM
VMM 陷阱处理程序模拟特权指令
也许将特权操作应用于"虚拟状态"
例如读/写 sepc
也许转换并应用于真实硬件
例如赋值给 satp
"陷阱并模拟"
很好，因为你可以完全在软件中构建这样的虚拟机
也许可以把 xv6 变成 RISC-V 的陷阱并模拟 VMM

哪些客户指令会陷阱？
csrr, csrw, ecall, sret, 设备内存的 ld/st

RISC-V 陷阱并模拟 VMM 需要保持什么虚拟状态？
所有"特权 CPU 状态"
CPU 状态，客户内核假设它可以读/写
但被用户模式禁止，通常必须与"真实"状态不同
模式
所有 s*寄存器（sepc, stvec, scause, satp 等）
页表
PLIC/CLINT设备硬件

RISC-V 在陷阱并模拟虚拟化方面很好
所有特权指令如果在用户模式下尝试执行都会陷阱
并非所有 CPU 都这么好--例如 32 位 x86
一些特权指令不会陷阱；x86 在用户模式下运行时忽略

对于 RISC-V 陷阱并模拟，当以下情况必须发生什么：
... 客户用户代码执行 ecall 进行系统调用？
[图：客户用户，客户内核，VMM，虚拟状态，真实 sepc]
CPU 陷阱到 VMM（ecall 总是生成陷阱）
硬件将客户的 PC 保存在（真实的）sepc 中
VMM 陷阱处理程序：检查客户指令
虚拟 sepc <- 真实 sepc
虚拟模式 <- 管理员
虚拟 scause <- 8 "系统调用"
真实 sepc <- 虚拟 stvec
修改（真实）页表--为非 PTE_U 条目设置 PTE_V
sret：从陷阱返回（将真实模式设置为用户）

... 客户内核读取 scause，例如 csrr a0, scause
陷阱到 VMM（因为 csrr 是特权指令）
检查客户指令
陷阱帧 a0 <- 虚拟 scause
真实 sepc += 4
从陷阱返回

... 客户内核执行 sret（返回到用户）？
CPU 陷阱到 VMM
VMM 陷阱处理程序：
虚拟模式 <- 用户
真实 sepc <- 虚拟 sepc
修改（真实）页表--清除非 PTE_U 条目的 PTE_V
从陷阱返回

... 客户内核写入 satp？
VMM 必须确保客户只能访问自己的内存
并且必须重新映射客户物理地址
VMM 设置从客户页表派生的"影子"页表
客户的页表：客户 va -> 客户 pa
VMM 为此客户映射
客户 pa -> 主机 pa
VMM 的"影子"页表
客户 va -> 主机 pa
VMM 在真实的 satp 中安装影子页表

... 客户内核修改活动页表中的 PTE？
VMM 不需要做任何事情
RISC-V 规范说 PTE 修改直到 sfence.vma 才生效
sfence.vma 导致陷阱到 VMM
VMM 生成新的影子页表

如何模拟设备？
例如磁盘，NIC，显示器
一大挑战！
策略#1：模拟常见的现有真实设备
需要运行无知的客户操作系统
拦截内存映射控制寄存器的读/写
通过将这些页面标记为无效，使 VMM 获得页面错误
VMM 将页面错误转换为对模拟设备状态的操作
例如，qemu 为 xv6 模拟 uart/console
qemu 将 uart 读/写转换为到你显示器或 ssh 的字符

策略#2：为效率量身定制的特殊虚拟设备
需要客户操作系统驱动程序--即客户知道它在虚拟机中
可以比拦截控制寄存器读/写更简化
例如，xv6 的 virtio_disk.c；qemu 转换为对文件 fs.img 的读/写

策略#3：直接访问真实硬件设备
客户操作系统直接访问设备硬件，无陷阱
通常需要设备中的特定支持
现代 NIC 为每个虚拟机有独立的 DMA 环
可以高效

陷阱并模拟工作得很好--但可能很慢！
大量陷阱到 VMM

*** 硬件支持的 x86 虚拟化
VT-x/VMX/SVM：硬件支持的虚拟化
现代 Intel（和 AMD）CPU 在硬件中支持虚拟化
客户可以执行特权指令而无需陷阱！
可以修改控制寄存器，更改页表，处理异常！
可以切换到用户模式，并接收系统调用陷阱等
比陷阱并模拟更快，且 VMM 软件更简单
广泛用于实现虚拟机
例如 WSL（Windows 子系统 for Linux），云
（这怎么可能安全？）

一些术语
每个 CPU 要么在根模式下--运行 VMM
即宿主
要么在非根模式下--运行客户（内核 + 用户进程）
执行在两者之间切换
VMCS（VM 控制结构）--配置，保存/恢复
特殊指令切换 VT-x 模式
VMLAUNCH/VMRESUME：宿主->客户
VMCALL：客户->宿主
某些事件也会强制客户->宿主"退出"

VT-x 必须防止客户做什么，给定对特权状态的访问？
读/写其自身内存之外的内容
与硬件设备通信，或抓取中断
干扰 VMM 宿主的控制寄存器设置
EPT（扩展页表）限制客户内存访问

问题：我们想让客户内核控制其自己的页表
我们也想限制客户只使用允许的物理内存
MMU 在 VT-x 客户模式中有*两*层地址转换
首先，%cr3 页表映射客户 va->客户 pa（照常）
其次，EPT 映射客户 pa->主机 pa
VMM 设置 EPT 只为客户的自己的内存有映射
客户无法看到或更改 EPT
所以：客户可以自由读/写%cr3，更改 PTE，读 D 位等
VMM 仍然可以通过 EPT 提供隔离
CPU 从普通（%cr3）页表传送页面错误到客户
EPT 的页面错误强制退出到宿主--客户看不到它们

设备和定时器中断
CPU 强制从客户退出，传送中断到宿主
VMCS 内存区域保存保存的宿主状态
VMLAUNCH 和 VMRESUME 保存所有宿主特权状态（寄存器等）
并恢复所有客户的（先前保存的）状态
从客户到宿主的退出恢复宿主的状态
所以客户无法扰乱宿主的特权状态
因此：如果宿主正确配置，客户无法逃脱
硬件虚拟化被广泛使用，例如在云中。

*** Dune
大想法：使用 VT-x 运行 Linux 进程（而不是运行客户内核）
然后应用程序代码可以直接快速访问页表，页面错误等
允许用户代码高效：
沙箱不受信任的代码
修改页表并处理页面错误

方案
[linux, dune 模块，进程]
Dune 是 Linux 的"可加载内核模块"
普通进程可以切换到"Dune 模式"
Dune 模式进程仍然是进程
有内存，可以进行 Linux 系统调用（通过 VMCALL）
隔离机制有点不同
VT-x 客户管理模式
通过 EPT 进行内存保护
页表
Dune 给予进程额外功能
读写自己的页表，包括 PTE D（脏）位
比 Linux mprotect() 系统调用更快
处理自己的页面错误
比让 Linux 将错误转换为信号处理程序的上调用更快
切换到（客户）用户模式，用于沙箱
客户用户模式只能使用客户 PTE_U 地址
并且不能使用特权指令/寄存器
进程可以拦截（客户）用户系统调用，页面错误

示例：沙箱执行（论文第 5.1 节）
假设你的网页浏览器想要运行第三方插件
例如视频解码器或广告拦截器
插件可能是恶意的或有错误的
浏览器需要"沙箱"
执行插件，但限制系统调用/内存访问
假设浏览器作为 Dune 进程运行：

浏览器创建带有 PTE_U 映射的页表用于内存
插件可以使用
和非 PTE_U 映射用于浏览器内存的其余部分
设置%cr3
sret 到不受信任的代码，在客户用户模式下
插件可以通过页表读/写允许的 PTE_U 内存
插件可以执行系统调用指令
但其系统调用陷阱到浏览器（而不是底层内核）
浏览器可以决定是否允许每一个
