HLL 自动消除内存安全错误！
HLLs 有垃圾收集器（GC）
GC 自动化内存释放
对程序员方便
...并提供内存安全
但 GC 有成本：
运行时 CPU 周期
延迟执行
额外内存
因此 HLL 使用是一个权衡：安全 vs 性能
确定性能成本对于理解此权衡很重要
以前没有对 HLL 内核进行过深入的性能评估
尽管研究人员已经构建了许多 HLL 内核
想要：更好地了解 HLL 内核性能
目标：将 HLL 内核性能与快速内核进行比较
即与 Linux 对比
Biscuit 开始于 2014 年
约 30k LOC 用 Go 编写
架构类似于 Linux 以进行更公平的比较
POSIX 系统调用
可以运行复杂应用程序（NGINX, Redis）而无需源代码修改
在许多方面类似于 Linux
一些差异：
内核线程是轻量级 goroutines
上下文切换不保存/恢复页表
不能解引用用户指针
手动转换
（什么是 SSE 寄存器/指令？）
Go 编译器自由使用 SSE 寄存器
而 Linux 避免使用 SSE
显式保存/恢复 SSE 寄存器
结果：Biscuit 更频繁地保存/恢复 SSE 寄存器
Go 不是为处理中断而设计的
运行时不在关键部分禁用/启用中断
在中断中调用关键部分（分配）
可能死锁
中断处理程序不能做很多
取而代之的是它们唤醒处理 goroutine 并返回

最大差异：处理 OOM
OOM 问题
Biscuit、Windows、Linux、FreeBSD 等都面临
（交换不能解决此问题，尽管可能使 OOM 不太可能）
许多内核操作分配内存
open(2) 分配一个文件对象
socket(2) 分配一个套接字对象
用户程序决定何时释放资源/释放内存
=> 用户程序决定内核使用多少堆内存
但机器有有限内存
问题：如果用户程序导致内核分配所有内存会怎样？
为什么会发生？
有错误的程序
数据库服务器故意使用大部分内存
+ 分配的不幸峰值
结果：几乎所有操作都无法成功直到内存被释放
硬或无法让用户程序合理处理
即 printf() 失败
甚至 exit(2) 失败！
由其他进程使用的内存
没有用户程序能取得进展
如何恢复？
需要释放内存
通过杀死内存占用进程来恢复内存
不能简单地杀死
exit(2) 必须分配来关闭文件并保持文件系统一致
结果：内核必须为 exit(2) 保留足够内存
Linux 和 Biscuit 都这样做
内核杀死占用者的方式很重要
Linux 的方法：
在分配器中阻塞很诱人
然后调用者不必处理失败
但这可能导致死锁
例如：好程序获取文件系统中目录的锁
内存占用者等待锁
内核无法杀死占用者
占用者等待好程序
好程序等待占用者退出
死锁
通过使好程序的分配失败来避免死锁
结果：内核必须处理几乎所有分配的失败
很难且充满错误

"太小而不能失败"规则
Biscuit 的方法
不能使用 Linux 的方法
在执行操作之前，等待直到有足够的内存
在操作中间没有等待
没有锁被持有
因此没有死锁
如何计算最大内存？
事实证明 Go 的静态分析很容易
编写了工具：MAXLIVE
高级别：精巧的逃避分析
不精确，但保守地高估所需内存，从不低估
检查调用图
找到每个系统调用的所有分配
两种对象：
1）可能写入全局
2）只被栈指针引用
类型 1 对象始终存活
类型 2 对象在某些栈帧销毁时释放
内存 = 类型 1 之和 + 在每个调用图叶节点的类型 2 的最大值
结果：没有死锁，几乎没有分配失败的处理
