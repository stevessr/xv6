6.1810 2024 第 10 讲：锁

为什么要谈论锁？
应用程序想要使用多核处理器以获得并行加速
所以内核必须处理并行系统调用，因此必须处理对内核数据的并行访问（缓冲区缓存，进程等）
锁有助于正确共享数据
锁可能限制并行加速

如果我们没有锁会发生什么？
案例研究：delete acquire/release in kalloc.c
启动内核工作！
运行 usertests
多次通过！
有些崩溃，我们失去了一些页面

为什么我们失去页面？
共享内存多处理器的图片
两个核心调用 kfree() 之间的竞争
糟糕：我们需要锁来确保正确性，但失去了性能（kfree 被序列化）

锁的抽象：
锁 l
acquire(l)
x = x + 1 -- "临界区"
release(l)

锁本身就是对象
如果多个线程调用 acquire(l)，只有一个会立即返回
其他人将等待 release() -- "阻塞"
程序通常有很多数据，很多锁
如果不同线程使用不同数据，那么它们可能持有不同锁，所以它们可以并行执行 -- 做更多工作。
注意锁 l 不是专门绑定到数据 x
程序员对对应关系有计划

决定何时需要锁的保守规则：
任何时候两个线程使用内存位置，至少一个是写操作
除非你持有正确的锁，否则不要触碰共享数据！
（太严格：程序逻辑有时可能排除共享；无锁）
（太宽松：printf()；不总是简单的锁/数据对应关系）

锁能自动吗？
也许语言可以将锁与每个数据对象关联
编译器在每次使用周围添加 acquire/release
程序员忘记的空间更少！
这个想法通常太僵化：
如果 present(table1, key1): add(table2, key1)
竞争：另一个线程可能在该线程有机会添加到 table2 之前从 table1 中删除 key1
我们需要：
锁 table1
锁 table2
present(..)
add()
解锁 table1；解锁 table2
也就是说，程序员通常需要对持有锁的代码区域进行显式控制，以便隐藏尴尬的中间状态

思考锁实现的方法
锁有助于避免丢失更新
锁帮助你创建原子的多步操作 -- 隐藏中间状态
锁帮助操作维护数据结构上的不变量
假设不变量在操作开始时为真
操作使用锁来隐藏不变量的临时违反
操作在释放锁之前恢复不变量

问题：死锁
注意 rename() 持有两个锁
如果：
核心 A 核心 B
rename(d1/x, d2/y) rename(d2/a, d1/b)
锁 d1 锁 d2
锁 d2 ... 锁 d1 ...
解决方案：程序员制定所有锁的顺序
所有代码必须按该顺序获取锁
即预测锁，排序，获取 -- 复杂！

锁与模块化
锁使在模块内部隐藏细节变得困难
为了避免死锁，我需要知道我调用的函数获取的锁
我可能需要在调用之前获取它们，即使我不使用它们
即锁通常不是各个模块的私人业务

锁与并行性
锁*阻止*并行执行
为了获得并行性，你通常需要以让每个核心使用不同数据和不同锁的方式来分割数据和锁
"细粒度锁"
选择最佳的数据/锁分割是一个设计挑战
整个 FS；目录/文件；磁盘块
整个内核；每个子系统；每个对象
你可能需要重新设计代码以使其在并行中工作良好
示例：将单个空闲内存列表分解为每个核心的空闲列表
如果有线程在单个空闲列表的锁上等待很多，这会有帮助
这样的重新设计可能需要大量工作！

锁粒度建议
从大锁开始，例如一个锁保护整个模块
较少死锁，因为较少持有两个锁的机会
较少需要推理不变量/原子性
测量以查看是否存在问题
大锁通常足够 -- 也许在该模块中花费的时间很少
只有在必要时才重新设计细粒度锁

RISC-V 硬件提供锁定内存位置的概念
不同的 CPU 有不同的实现
图：核心，总线，RAM，锁东西
所以我们实际上是把问题推到硬件
硬件以缓存行或整个总线内存锁的粒度实现
内存锁强制并发沼泽一次运行一个，而不是交错

看看 xv6 自旋锁实现
acquire(l){
while(__sync_lock_test_and_set(&lk->locked, 1) != 0)
}
如果 l->locked 已经是 1，sync_lock_test_and_set 设置为 1（再次），返回 1，循环继续自旋
如果 l->locked 是 0，最多一个 lock_test_and_set 会看到 0；它会设置为 1 并返回 0；其他 test_and_set 将返回 1
这是一个"自旋锁"，因为等待核心在获取循环中"自旋"

细节：内存读/写排序
假设两个核心使用锁来保护计数器 x，我们有一个天真的锁实现
核心 A：核心 B：
locked = 1 x = x + 1
while(locked == 1) locked = 0
... 
locked = 1 x = x + 1
locked = 0

编译器和 CPU 重新排序内存访问
即它们不遵守源程序的内存引用顺序
例如，编译器可能为核心 A 生成此代码：
locked = 1
locked = 0
x = x + 1
即将增量移到临界区外面！

合法行为称为"内存模型"
release() 对__sync_synchronize() 的调用防止重新排序
编译器不会将内存引用移动到__sync_synchronize() 之后
并且（可能）发出"内存屏障"指令来告诉 CPU
acquire() 对__sync_synchronize() 的调用有类似效果：
如果你使用锁，你不需要理解内存排序规则
如果你想要编写奇特的"无锁"代码，你需要它们

为什么要自旋锁？
它们在等待时不会浪费 CPU 吗？
为什么不放弃 CPU 并切换到另一个进程，让它运行？
如果持有线程需要运行；等待线程不应该让出 CPU 吗？

自旋锁指南：
持有自旋锁的时间非常短
持有自旋锁时不要让出 CPU
系统为较长的临界段提供"阻塞"锁
等待线程让出 CPU 但开销通常更高
你稍后会看到一些 xv6 阻塞方案

建议：如果不需要就不要共享
从几个粗粒度锁开始
为你的代码添加仪器 -- 哪些锁阻止了并行性？
仅在需要并行性能时使用细粒度锁
