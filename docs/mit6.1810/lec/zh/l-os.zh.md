无操作系统的主问题：缺乏隔离
资源隔离：一个应用程序使用太多内存，或占用 CPU，或使用所有磁盘空间
内存隔离：一个应用程序的错误写入另一个的内存

Unix 系统调用接口以有助于隔离的方式限制应用程序
通常通过抽象硬件资源
fork() 和进程抽象核心
操作系统透明地在进程之间切换核心
强制进程放弃它们
可以有比核心更多的进程
exec()/sbrk() 和虚拟地址抽象 RAM
每个进程都有自己的内存 -- 地址空间
操作系统决定将应用程序放在内存的何处
操作系统将进程限制在使用自己的内存
文件抽象磁盘级块
操作系统确保不同用途不冲突
操作系统执行权限
管道抽象内存共享
系统调用接口经过精心设计以提供隔离
但仍然允许受控共享和可移植性

隔离既关乎安全也关乎错误

操作系统设计师对安全做了什么假设？
我们假设用户代码是积极恶意的
积极试图突破隔离
积极试图欺骗系统调用做愚蠢的事情
积极试图干扰其他程序
我们假设内核代码是可信的
我们假设内核开发者是善意和有能力的
我们不太担心内核代码滥用其他内核代码。
当然，内核中仍有错误
所以内核必须小心对待所有用户交互
=> 需要安全思维
内核中的任何错误都可能是安全漏洞
[在安全术语中，内核在可信计算基础 (TCB) 中]

内核如何保护自己免受用户代码侵害？
两个主要组成部分：
硬件级对用户指令的控制
小心的系统调用接口和实现
硬件级隔离
CPU 和内核是共同设计的
\- 用户/管理模式
\- 虚拟内存
用户/管理模式（也称为内核模式）
管理模式：可以执行"特权"指令
例如，设备硬件访问
例如，修改页表
用户模式：不能执行特权指令
内核在管理模式，应用程序在用户模式
[RISC-V 还有 M 模式，我们大多忽略]

处理器提供虚拟内存页表映射 VA -> PA
限制用户进程可以使用的内存
操作系统设置页表，使每个应用程序只能访问自己的内存
并且无法访问内核的内存
页表只能在管理模式下更改
我们将花大量时间查看虚拟内存...

系统调用如何工作？
应用程序在用户模式下运行
系统调用必须在内核的管理模式下执行
必须以某种方式允许应用程序访问特权资源！

解决方案：以受控方式更改模式的指令
open(): ecall
ecall 做几件事
切换到管理模式
开始在内核代码中的已知点执行
内核期望在代码的那个点接收控制
有点复杂，将在后续讲座中讨论

旁白：可以在没有硬件支持的用户/管理模式和虚拟内存的情况下实现进程隔离吗？

但用户只能使用批准的语言/编译器

让我们特别看看 xv6
xv6 只在 RISC-V CPU 上运行，并需要周围设备的特定设置 -- 板子
模拟"SiFive HiFive Unleashed"板子
hifive.pdf
一个简单的板子（例如，无显示器）
\- 带 4 个核心的 RISC-V 处理器
\- RAM（128 MB）
\- 用于控制台的 UART
\- 磁盘类存储
\- 以太网
\- 这样的板子相当便宜，虽然不强大

Qemu 模拟这个 CPU 和类似的板子设备
\- 称为"virt"，如"qemu -machine virt"
https://github.com/riscv/riscv-qemu/wiki
\- 接近 SiFive 板子（https://www.sifive.com/boards）
但磁盘使用 virtio

这块板子上的 RISC-V 芯片内部有什么？
四个核心，每个有 32 个寄存器
ALU（add, mul, 等）
MMU 控制寄存器
定时器，中断逻辑
总线接口
核心大致独立，例如每个有自己的寄存器
它们共享 RAM
它们共享板子设备

什么是模拟？
忠实模拟硬件的 C 程序
例如，RISC-V CPU：
uint64 reg[32];
for (;;) {
读取 RISC-V 指令
解码 RISC-V 指令（ld, add, sub）
执行 RISC-V 指令（add reg[0] <- reg[0] + 7，对于 ld t0, 7）
}
