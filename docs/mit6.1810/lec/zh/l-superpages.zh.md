6.1810 2025 L9：分页到磁盘，超页

实践，透明的操作系统对超页的支持，Navarro, Iyer, Druschel, 和 Cox, OSDI 2002。

大纲：
经典 O/S 分页
TLB 考虑
今天论文的重要观点

上一讲的重要观点：页面分配通常是懒惰的（比 xv6 上多得多）
程序启动时，其页表可能完全为空
程序分配内存时，其页表通常不会改变！
程序首次*访问*页面时：
页面错误
内核分配物理页面，初始化（清零，或从文件读取）
映射到页表中

为什么？
透明
快速启动程序
程序可以请求大量内存而不必担心 RAM 大小
页表的原始目的：支持比 RAM 更大的应用程序
仅仅一个，或许多个，总量很大
追溯到内存相对较贵的时代
仍然有用且值得了解（也是今天论文的背景）
"分页"或"分页到磁盘"

分页到磁盘如何工作？
即如何让程序认为它们有更多的内存比实际 RAM？
玩具示例：机器只有两个页面的 RAM，但程序想要使用 4 个页面的数据
图：页表：4 个 PTE
RAM：两个物理内存页面，最初空闲
磁盘：4 个"分页"存储页面，一个页面的可执行文件

读取页面错误在 va 0
内核处理页面错误透明地
分配物理页面#1
从可执行文件读取
PTE0 -> pa1

写入页面错误在 va 2（实际上是 va 0x2000，第 3 页）
分配物理页面#0
清零它
PTE2 -> pa0

写入页面错误在 va 1
没有空闲 RAM：现在怎么办？
选择一个非空闲物理页面，假设是物理页面#0
将物理页面#0 写入磁盘页面 2
我们知道必须保存它，因为 PTE2 将有脏位设置
PTE2 -> 无效
记住 va 2 在磁盘上的位置
"驱逐"或"页面输出"或"替换"

初始化物理页面#0 用于 va 1
PTE1 -> pa0

va 2 的页面错误（读或写）
让我们驱逐物理页面#1（va 0）
将页面#1 写入磁盘块#1
PTE0 无效
让我们"页面输入"虚拟页面 2 到物理页面#1
PTE2 -> pa1

我们使用 RAM 作为缓存，磁盘用于"后备存储"
现在内存很大，为什么例如 Linux 支持分页到磁盘？
当分页被发明时，内存很小（< 1 MB）且昂贵
现在计算机个人很便宜，有 GB 的内存
但内存仍然是巨大的开支
例如在数据中心，总内存成本通常超过 CPU
程序和数据继续增长更大
因此 O/S 优化 RAM 使用仍然重要
页面替换仍然重要：管理文件缓存
非常大的程序
内存映射巨大的文件
避免硬边缘

驱逐策略非常重要：
如果我们驱逐一个页面，而它本身即将被使用，
那将导致另一次页面错误和磁盘读取
磁盘读取大约需要一毫秒
这是一百万条指令！
错误进程必须等待...
糟糕的驱逐策略可能导致大量耗时的页面错误

想法：驱逐距离现在最长使用时间的页面
不幸的是，一般来说内核无法预测这将是哪个页面
所以我们需要易于实现的驱逐启发式方法

人们发明了许多驱逐策略
常见的驱逐策略：最近最少使用（LRU）
内核维护所有物理页面号的 LRU 列表
内核定期扫描所有物理页面
查找每个页面的 PTE，查看"访问"位
如果访问位被设置，将页面移动到 LRU 列表的头部并清除访问位
所以如果页面被频繁使用，它会不断被移动到 LRU 列表的头部
当页面错误需要物理内存页面时，从 LRU 列表的尾部获取
驱逐页面时，需要使引用它的所有 PTE 无效
可能不止一个：写时复制 fork，内存映射文件，共享内存
通常内核有一个"反向映射"，将 PA 映射到页面表和 VA 列表
最好驱逐干净页面而不是脏页面
干净==磁盘上已经有相同的副本
来自先前的页面输出，或在只读可执行文件中
我们可以重新使用干净页面而无需首先将其写入磁盘
只需清零它，并调整旧的和新的 PTE

更复杂的 LRU 方案（论文第 5.1 节的 FreeBSD 方案）
三个 LRU 列表：活动，非活动，缓存
定期扫描；如果访问（在任何列表上），移动到活动列表头部
如果内存紧张：移动活动列表尾部到非活动列表
将脏的非活动页面写入磁盘
移动干净的非活动列表尾部到缓存列表
所以缓存列表只包含一段时间未使用的干净页面
它是为页面错误分配的缓存页面
保持缓存列表非空对于快速页面错误很重要
如果"内存压力"，扫描更快，将脏页面更快写入磁盘
内存压力=缓存 LRU 列表太短

什么时候分页到磁盘工作良好？
如果应用程序在任何给定时间只使用其内存的一小部分
所以活动内存可以保存在 RAM 中，其余分页到磁盘
"引用局部性"
"工作集"
工作集可能随时间变化，但希望缓慢
这对许多程序来说是真实的，但不是全部

如果程序的工作集太大怎么办？
或者运行的程序太多怎么办？
内核将驱逐即将需要的页面
大量内存访问将产生页面错误和磁盘读写
磁盘比 RAM 慢得多，系统将显著变慢
"颠簸"

LRU 是好计划吗？
LRU 实际上是一种预测：最近使用=>将再次使用
通常工作良好但有时非常糟糕！
示例：通过巨大内存的重复顺序扫描
程序可能在*每个*页面上出现错误
最近最少使用的页面将是程序即将访问的页面！
所以，对于这个程序，LRU 是可怕的替换策略
因此一些系统使用随机替换，或提供它作为选项

页面应该多大？
假设只有一种大小
CPU 设计师选择页面大小，内核必须接受它
很久以前：小，例如 512 字节
现在通常是 4096（但论文使用 8k，有些更大）

为什么偏好大页面？
页表消耗的内存更少
16 GB -> 32 MB 的 PTE 如果 4k 页面
更少的 CPU 和内存用于内核簿记
空闲列表，反向映射，VMA
更少的页面错误（假设良好的引用局部性）

为什么偏好小页面？
更少的 RAM 浪费用于部分使用的页面
所以对于给定的工作负载可能需要更少的 RAM
对 PTE 访问和脏位的更精细粒度
所以内核可以更精确地在 RAM 中保持所需数据
每次页面输入和页面输出的磁盘 I/O 更少，所以页面错误延迟更低

大页面和小页面都有吸引人的属性

今天的论文是关于 O/S 支持*两种*页面大小

今天论文的最后背景：TLB
翻译后备缓冲区
虚拟到物理地址转换的 CPU 缓存
它是 va,pa 表[图：核心，L1，L2，RAM，然后添加 TLB]
每个内存引用都需要 va 到 pa 查找
ld, st, 指令获取
所以 CPU 需要能够每周期大约做一个 -- 纳秒
TLB 通常很小，因为它必须非常快
论文：128 个条目
现代 CPU：128 个 L1 条目，1024 个 L2 条目

TLB 的"覆盖范围"是多少？
128 个条目，4k 页面：半兆字节！
1024 个条目：四兆字节
这在机器和程序规模上很小，具有>= 16 GB 的 RAM
定期使用更多内存的程序将在 TLB 中未命中

TLB 未命中的代价是什么？
RISC-V CPU 遍历多级页表以获取叶 PTE（RISC-V 硬件处理 TLB 未命中，不是内核）
这是几次内存获取，每次最多 100 纳秒
数百个周期（尽管 CPU 数据缓存可能有帮助）
CPU 可能停顿直到 TLB 填充
所以 TLB 未命中可能使指令时间增加约 100 倍

大页面是增加 TLB 覆盖范围的方法
128 个 TLB 条目 * 2MB 页面 = 1/4 GB
现代 CPU 确实有至少这么大超页

但巨大页面可能浪费大量 RAM！
因为一些程序只使用每个页面的一小部分

能够混合小页面和超页是有吸引力的
你们都熟悉基本概念！

今天论文的目标：
内核自动选择基础页面和超页以增加 TLB 覆盖范围，
减少 TLB 未命中浪费的时间
适应程序特征，包括行为变化
应对大程序和小程序，紧张和宽松的内存压力
透明地做--经典的内核策略

给进程一个 2MB 超页实际上是预测：
进程将在不久的将来密集使用那个 2MB
而不是例如只使用 2MB 中的几千字节
如果错了->浪费 RAM

紧张：更少的 TLB 未命中 vs 浪费的 RAM

今天论文解决的三个令人困惑的设计问题，
后续研究，真实内核例如 Linux

* 什么时候内核应该给应用程序一个超页（PTE 和 2MB 的 RAM）？
应用程序调用 sbrk() 时？
很难从 sbrk() 大小参数猜测情况。
sbrk(2MB) 可能不意味着进程将使用内存。
sbrk(4096) 可能是完整 2MB 分配中的第一页。
应用程序在 2MB 区域内发生第一次页面错误时？
（这是 Linux 的方法之一）
至少我们知道它将使用一些 RAM
但可能不是全部，导致 RAM 浪费
应用程序将立即从超页中受益
这是一个赌注，超页通常是合适的
可能是个好计划，特别是如果有很多 RAM，少数大应用程序
应用程序在 2MB 区域内的所有页面都发生页面错误时？
将区域转换为超页（这是论文的方法）
好：我们知道它使用了 2MB 超页的 100%
坏：我们让它执行了相当长的时间而没有超页的好处
这是一个保守的方法，优先考虑不浪费内存

* 内核如何找到合适的 2MB RAM 区域？
必须是连续的，2MB 对齐，且空闲
2MB 长的空闲运行很少偶然发生！
物理内存通常"碎片化"--使用和空闲的 4k 页面交错
对 4k 页面不是问题，对使用 4k 和 2MB 是大问题
同时使用 4k 和 2MB？
在启动时分配一些 2MB RAM 区域？（这是实验建议的，为简单起见）
但有多少？如果需要更多或更少怎么办？
在需要时移动（复制）物理页面以清理 2MB？
"压缩"或"去碎片化"
并修补移动页面的 PTE（这是 Linux 的方法之一）
导致分配或首次使用变慢，使用 CPU 压缩
论文建议了一个聪明的分配计划（第 4.1 节）
在新 2MB 区域中发生第一次错误时，创建一个普通 PTE，
分配并初始化一个页面
但也从 LRU"缓存"列表中保留 2MB 的页面
这些是长时间未使用的干净页面
论文实际上不分配或初始化或映射那些页面
所以它们仍然保存其在原始映射被使用时缓存的内容
随着超页中发生更多错误，分配更多保留的页面，并初始化它们
当 2MB 区域中的所有普通页面都发生错误时，升级为超页

问题：为什么这种安排是好的？

* 内核有时需要降级超页
如果内存紧张；较小的页面可能需要较少的 RAM
哪些超页应该被降级？
问题：2MB 粒度
访问位使很难判断什么是真正使用的
所以分解超页以获得更细粒度的访问位
也：也许如果进程写入超页
不想让单个写入（后来）导致整个 2MB 的页面输出
所以读保护超页，在第一次写入时降级，
然后可以从更细粒度的脏位中受益

超页的典型改进是 10%
有时更高

当前状况？
最容易跟踪 Linux；网上有很多帖子。
对某些应用程序非常有价值。
但"透明大页面"在其他情况下浪费大量内存，
由于 2MB 中只有一小部分实际使用。
所以设计细节随着时间发生了很大变化。
谨慎的应用程序通常明确分配它们的超页。
仍在积极发展。
也许根本问题在于收益通常相当适度，
但成本（内存浪费）可能非常大。
