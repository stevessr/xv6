计划
  问题：崩溃恢复
    崩溃导致磁盘上文件系统不一致
  解决方案：
    预写日志记录

# 为什么需要崩溃恢复

什么是崩溃恢复？
  你正在写文件系统
  然后断电了
  你重启
  你的文件系统还能用吗？

问题：
  多步骤操作期间的崩溃
  可能导致 FS 不变量被违反
  重启后：
    坏：因损坏的 FS 再次崩溃
    更坏：没有崩溃，但读/写错误的数据

示例：
  创建：
  
    $ echo hi > x
    // 上节课的创建追踪：
    bwrite: block 33 by ialloc   // 在 inode 块 33 中分配 inode
    bwrite: block 33 by iupdate  // 更新 inode（例如，设置 nlink）
    bwrite: block 46 by writei   // 写入目录项，通过 dirlink() 添加"x"
    bwrite: block 32 by iupdate  // 更新目录inode，因为inode可能已更改

    iupdate和writei之间的崩溃
      分配文件inode
      崩溃：inode未被释放但未使用——不太好

    如果文件系统先写46和32然后写33会怎样
      如果在32和33之间的崩溃，那么目录项指向空闲inode——灾难！
      再次崩溃，或者更糟，如果inode被分配给其他东西

  写入：
    inode addrs[]和 len
    间接块
    块内容
    块空闲位图
    崩溃：inode 指向空闲块——灾难！
    崩溃：块未被释放但未使用——不太好
    
  取消链接：
    块释放位图
    释放 inode
    擦除目录项

我们能期望什么？
  重启并运行恢复代码后
  1. FS 内部不变量保持
     例如，没有块同时在空闲列表中和在文件中
  2. 除了最后几个操作外，所有的都保存在磁盘上
     例如，我昨天写的数据被保留
     但在崩溃时正在写的数据可能没有
     所以用户可能需要检查最后几个操作
  3. 没有顺序异常
     echo 99 > result ; echo done > status

正确性和性能经常冲突
  磁盘写入很慢！
  安全 => 尽快写入磁盘
  速度 => 不写磁盘（批处理，写回缓存，按磁道排序，等等）

崩溃恢复是一个反复出现的问题
  出现在所有存储系统中，例如数据库
  这些年来已经有大量的工作致力于解决方案
  许多巧妙的性能/正确性权衡

# 日志记录解决方案

最流行的解决方案：日志记录（==日志） 
  目标：针对崩溃的原子系统调用
  目标：快速恢复（没有小时级的 fsck）

将分两步介绍日志记录
  首先是 xv6 的日志，它只提供安全性和快速恢复
  然后是 Linux EXT3，它在正常操作中也很快

日志记录的基本思想
  你想要原子性：全部系统调用的写入，或全部不
    让我们将原子操作称为"事务"
  记录系统调用*将要*在磁盘上的日志中完成的所有写入
  然后在磁盘上记录"完成"（提交）
  然后执行 FS 磁盘写入（安装）
  在崩溃 + 恢复时：
    如果日志中"完成"，重播日志中的所有写入
    如果没有"完成"，忽略日志
  这是预写日志

预写日志规则
  除非事务的所有写入都在磁盘上的日志中，
  并且记录的写入被标记为已提交，否则不在磁盘上安装事务的任何写入。

为什么有这个规则？
  一旦我们已将一个写入安装到磁盘上的 FS，
  我们必须执行事务的所有其他写入
  ——这样事务是原子的。我们必须
  准备好在第一次安装写入后的崩溃
  所以其他写入在崩溃后必须仍然可用
  ——在日志中。

日志记录是魔法
  复杂可变数据结构的崩溃恢复通常很困难
  日志通常可以分层在现有存储系统上
  并且它与高性能兼容（下节课的主题）

# xv6 日志记录概览

xv6 日志表示
  [图表：缓冲区缓存，内存中日志块号数组，
            磁盘上的 FS 树，磁盘上的日志头和块]
  在写入时将块号添加到内存数组
  将数据本身保留在缓冲区缓存中（固定）
  在提交时：
    将缓冲区写入磁盘上的日志
    等待磁盘完成写入（"同步"）
    将日志头扇区写入磁盘
      块号
      非零"n"
  提交后：
    将日志中的块安装（写入）到 FS 中的家位置
    解除固定块
    将零写入磁盘上日志头中的"n"

磁盘上日志头中的"n"值表示提交
  非零 == 已提交，日志内容有效且是完整事务
  零 == 未提交，可能不完整，恢复应忽略日志
  非零"n"的写入是"提交点"
  
xv6 磁盘布局及块号
   2: 日志头
   3: 记录的块
  32: inodes
  45: 位图
  46: 内容块

让我们看一个例子。
  我修改了 bwrite() 以打印低级磁盘写入，
  即事务提交期间发生的磁盘写入。

  $ echo a > x
  
  // 创建
  bwrite 3    // inode, 33
  bwrite 4    // 目录内容，46
  bwrite 5    // 目录 inode, 32
  bwrite 2    // 提交（块号和 n）
  bwrite 33   // 安装 x 的 inode
  bwrite 46   // 安装目录内容
  bwrite 32   // 安装目录 inode
  bwrite 2    // 标记日志"空"
  // 写入
  bwrite 3
  bwrite 4
  bwrite 5
  bwrite 2
  bwrite 45   // 位图
  bwrite 595  // a  (注意：bzero 被吸收)
  bwrite 33   // inode (文件大小)
  bwrite 2
  // 写入
  bwrite 3
  bwrite 4
  bwrite 2
  bwrite 595  // \\n
  bwrite 33   // inode
  bwrite 2

让我们看看第 2 个事务，一个 write()
  首先是 file.c:syswrite 
    计算在日志满之前我们可以写入多少块
    在一个事务中写入那么多块

  结合 fs.c:writei
    begin_op()
      bmap() -- 可以写入位图，间接块
        log_write 到 bzero 新块
      bread()
      修改 bp->data
      log_write()
        吸收 bzero
      iupdate() -- 写入 inode
    end_op()

  log.c 中的 begin_op()：
    需要指示哪组写入必须是原子的！
    需要检查日志是否正在提交
    需要检查我们的写入是否适合日志的剩余部分
  log_write()：
    将扇区号添加到内存数组
    bpin() 将固定缓存中的块，这样 bio.c 不会驱逐它
  end_op()：
    如果没有未完成的操作，提交
  commit()：
    将更新的块从缓存复制到磁盘上的日志
    在磁盘上的日志头中记录扇区号和"完成"
    安装写入 -- 从磁盘上的日志复制到磁盘上的FS
      bunpin()将从缓存中解除固定---现在它可以被驱逐
    从日志中擦除"完成"

如果在事务期间崩溃会怎样？
  内存丢失，只留下崩溃时的磁盘
  内核在启动时调用 recover_from_log()，在使用 FS 之前
    如果日志头块说"完成"：
      将块从日志复制到磁盘上的真实位置
  磁盘上的日志中有什么？
    提交前的崩溃
    提交期间的崩溃 -- 提交点？
    install_trans() 期间的崩溃
    重新启动后，正在 recover_from_log() 中的崩溃
  注意：多次重播日志是可以的！
    只要没有其他活动介入

注意 xv6 假设磁盘是故障停止的
  它要么正确地执行写入，要么不执行写入
    即，也许由于断电它无法执行最后一次写入
  因此：
    没有部分写入（每个扇区写入都是原子的）
    没有乱写
    没有扇区退化（没有读取错误）
    没有读取错误的扇区

# 挑战
  
挑战：防止写回缓存
  一个系统调用可以安全地更新一个*缓存的*块，
    但该块不能写入 FS
    直到事务提交
  棘手的是，例如缓存可能耗尽空间，
    并且被诱惑驱逐一些条目
    为了读取和缓存其他数据。
  考虑创建示例：
    将脏 inode 写入日志
    将 dir 块写入日志
    驱逐脏 inode
    提交
  xv6 解决方案：
    确保缓冲区缓存足够大
    在缓冲区缓存中固定脏块
    提交后，解除固定块
  
挑战：系统调用的数据必须适合日志
  xv6 解决方案：
  - 计算每个系统调用写入块数的上限
    设置日志大小 >= 上限
  - 将一些系统调用分解为几个事务
    例如，大 write()s
    因此：大 write()s 不是原子的
      但崩溃将留下写入的正确前缀
	
挑战：允许并发系统调用
  必须允许来自几个调用的写入在日志中
  在提交时必须全部写入它们
  但不能写入仍在事务中的调用的数据

xv6 解决方案
  如果日志可能不适合其数据，则不允许新的系统调用开始
    必须等待当前调用完成并留出足够空间在日志中
    或者，等待并发调用已提交，这会释放日志
  当进行中的调用数量下降到零
    提交
    释放日志空间
    唤醒等待的调用

挑战：一个块在事务中可能被多次写入
  log_write() 仅影响内存中的缓存块
  所以一个缓存块可能反映多个未提交的事务
  但安装仅在没有进行中的事务时发生
    所以安装的块仅反映已提交的事务
  对性能有好处：\"写入吸收\"

# 总结

xv6 的日志设计有什么好的？
  由于预写日志的正确性
  良好的磁盘吞吐量：日志自然地批处理写入
    但数据磁盘块被写入两次
  并发性
  
xv6 的日志记录有什么问题？
  不是很高效：
    每个块被写入两次（日志和安装）
    记录整个块，即使只有几个字节被修改
    同步写入每个日志块
      可以将它们作为一个批处理写入，只同步写入头 
    日志写入和安装写入是急切的
      两者都可以是懒惰的，为了更多的写入吸收
      但仍然必须首先写入日志
  对于不适合日志中的操作有问题
    unlink 可能在截断文件时使许多块变脏
